## Desktop updates, in recommended priority order

### 1. Bring Watch Together synchronization up to the new room timing model

This is the most substantial native playback work in the range. Commands now describe position **at `execute_at`**, and a late client projects that position forward. The current reference documents measured round-trip clock sampling, gradual pitch-preserved rate convergence for 0.4–5 seconds of drift, a continuous rate-only loop, bounded reload recovery, and reports identifying the last applied command. Its normal convergence rate is 0.96–1.04, rather than aggressive seek/rate jumps. Buffering barriers must not rewind healthy guests to a stalled guest's position.

Desktop already has room command scheduling and drift code; it is not missing Watch Together wholesale. Its existing coordinator/controller still uses older clock, late-command and catch-up semantics. Port the new shared behavior through those existing native seams, verify command identity/readiness and repeated seek requests, and exercise native buffering/reload recovery. This is not evidence that ordinary single-user direct-play buffering has the same cause.

Concrete native seams: `WatchTogetherCoordinator.cs:217` clamps a late delay to zero but forwards the unchanged position; `WatchTogetherViewModels.cs:479,753` estimates offset from issued/arrival time and ignores pong RTT; `WatchPartySyncController.cs:278` seeks for reachable drift above 0.35 seconds and otherwise uses a 0.9–1.25 rate branch only within two seconds. Ordinary state reports at controller `:261` omit the applied command ID, while readiness already sends it. The server still accepts a report without that optional ID, so this is a significant alignment task **not a breaking mandatory protocol migration or reproduced current runtime failure**.

Source: [current synchronization contract](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/watch-party-synchronization.md), [current room clock](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/player/utils/roomClock.ts), [room convergence](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/player/utils/roomSyncCatchup.ts). Detailed native mappings are in `.codex-tmp/upstream-oct16-playback-audit.md`.

### 2. Remove retired built-in Trakt flows and handle migrated data correctly

Upstream deliberately removed Trakt collection import/sync, templates, trending and its built-in watch-sync provider. The v2 Trakt import routes are gone. Server migrations convert existing Trakt collections to manual collections while retaining their titles, stop syncing, and rewrite/disable Trakt trending rows. Imported watch history is retained. Built-in Trakt connections and credentials are removed by the server migration; the desktop must not attempt those infrastructure/data migrations itself.

Desktop still has `CollectionsApi.ImportUserTraktCollectionAsync` at `/api/v2/collections/import/trakt` (`Core/Api/CollectionsApi.cs:108`), Trakt template handling (`CollectionsViewModel.cs:593`), Trakt collection editor branches, legacy Home layout preservation/guards (`HomeLayoutMerge.cs`, `HomeSectionWritePolicy.cs`, `HomeLayoutTransferService.cs`) and visible copy (`CollectionsPage.xaml:147`, `SettingsPage.xaml.cs:947`). Remove obsolete built-in affordances and reconcile the new manual collection/Home import behavior. The server no longer returning a Trakt template may already hide some dead paths; the existence of those paths alone is not proof that every current user sees a failing button. Preserve generic provider/plugin support and unrelated imported history.

Sources: [breaking removal commit](https://github.com/Silo-Server/silo-server/commit/1e0b14a5cfa721df77a 65adf8c0a11ca1d712828), [collection/Home migration](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/migrations/sql/20261016131356_retire_trakt.sql), [watch-sync migration](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/migrations/sql/20261016134645_retire_trakt_watch_sync.sql), [provider/plugin contract](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/watch-provider-plugins.md).

### 3. Make subtitle appearance and timing follow the profile

The WebUI now saves `playback.subtitle_appearance` at profile scope and clears a shadowing device override. Reset clears both relevant scopes, allowing the contract default. Both Settings and the player use the same writer. `player.subtitle_sync_ms` gains profile scope at **manifest revision 19**; older servers still require a device-scoped fallback. The Language & Subtitles page gains an offset control and updated copy.

Desktop reads effective appearance, but both `SettingsViewModel.cs:1552` and `SubtitleAppearanceDialog.xaml.cs:195` still save `profile_device`; reset only deletes that device row. The player's manual delay (`PlayerOverlay.xaml.cs:1485`) updates `_subtitleDelayMs` and mpv `sub-delay`, without writing the new profile preference. The typed integer key already exists in `SettingsV2Values`, and the Your Devices editor can retain explicit device overrides; those are not substitutes for the new profile/default player flow. Add a shared captured-authority reader/writer, preserve SiloCast playback ownership, gate the new timing scope on revision 19, apply resolved offset at playback start, and update reset/pending/realtime presentation.

Sources: [appearance writer](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/hooks/queries/subtitleAppearance.ts), [timing writer/fallback](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/hooks/queries/subtitleSync.ts), [revision 19 manifest](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/contracts/settings/v1/manifest.json), [Settings presentation](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/pages/settings/SubtitleAppearanceSettings.tsx).

### 4. Add Not Interested and its management list

Movies/series gain **Not Interested** / **Show in Recommendations** in menus/detail actions and a list under Settings > Personalize. Capability: `GET /api/v2/capabilities/not-interested`; mark/unmark: `PUT`/`DELETE /api/v2/not-interested/{item_id}`; paginated list and single-mark GET are provided. Cards carry `user_state.not_interested`, with `user_state.changed` updates. Recommendations/discovery exclude marked titles and downrank similar ones; library browsing, search, playback, Favorites and Watchlist keep them. This is not the existing remove-from-Continue-Watching operation.

Desktop's shared `UserState` (`HomeSectionsResponse.cs:196`) has no NotInterested field; there are no corresponding API/menu/detail/Personalize handlers. Implement the optional capability, current-profile mutations/rollback, field-preserving state reconciliation, paged undo list and targeted recommendation invalidation, without hiding library/search cards or rebuilding all Home rows.

### 5. Add notified-series browsing and per-series mute/unmute

Notifications gains a **Series** view explaining which shows can notify the profile and why, with active/inactive and relationship filters, search, sorting and cursor paging. It can mute/unmute an individual series for that profile across notification channels. The list includes muted shows so users can undo a mute even when no interest reason remains. Capabilities advertise `series.available` and `series.mute`; API routes are `GET /api/v2/notifications/series` and `PUT`/`DELETE /api/v2/notifications/series/{id}/mute`.

Desktop currently has inbox/preferences/destinations (`NotificationsApi.cs`, `NotificationsPage.xaml`, `NotificationsModels.cs:164`), but no new series capability, DTOs, list or mute operations. Add the current list, explanatory relationship/next-up copy and current-profile writes. Muting must not remove a show from Home, history, Favorites or Watchlist; it also does not explain/repair the old intermittent Next Up removal exception.

Sources: [notification API](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/notifications-api.md), [Series UI](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/components/notifications/NotifiedSeriesList.tsx), [inbox entry points](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/pages/Notifications.tsx).

### 7. Add profile management entry points to Who's watching

The picker now offers **Add profile** alongside existing profiles and **Manage profiles**. It verifies the primary profile's PIN when needed. Creating uses captured primary authority/libraries without switching the viewer to that profile; managing switches to the verified primary and opens profile settings. Cancellation must retire a pending PIN result.

Reuse current editor/authority boundaries and add these entry points rather than recreating all profile management.

## Optional native feature and verification-only changes

**Signed-in LAN routing:** the server now advertises a trusted LAN connection path for signed-in native clients. Desktop has no corresponding pinned local-route/SPKI implementation. This is a useful optional connection feature, not a prerequisite for the current manually configured server URL or evidence of a fix for historical buffering. Any implementation needs the server identity/pinning and authorization contract, not an automatic switch to an arbitrary LAN host. Sources: [discovery](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/server-discovery.md), [server identity](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/server-identity.md).

**Measured/network-aware Auto quality:** the new optional `bandwidth_probe_v1` endpoint measures API-path throughput and the WebUI adds observed-throughput/stall-based downshift. Native already models bandwidth/cap fields, but `PlaybackManager.cs:129,533` does not supply a measurement and hardcodes unmetered. Native does not have Chromium's artificial 10 Mbps downlink ceiling; it should not copy that browser-specific workaround. Adding real native estimates, metered-network behavior and guarded Auto downshift is a separate substantial enhancement, with media-node-path awareness and cancellation. The new server endpoint is not evidence of a cure for existing native buffering. Sources: [bandwidth API](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/playback-api.md), [Auto downshift](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/web/src/player/hooks/useAutoQualityDownshift.ts).

**Artwork without server caching:** upstream now serves provider artwork URLs directly when image caching is disabled and tightens the server's artwork fetch guard. `ImageService.cs:179` already downloads the URL provided rather than requiring a Silo-hosted proxy, so source inspection does not establish a required native rewrite. Verify provider URL loading, fallback and source URL cache identity with caching off. Sources: [artwork setting behavior](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/settings-api.md), [artwork trust boundary](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/outbound-address-guard.md#serving-catalog-artwork).

**API restart and socket hardening:** current native does not opt into `header_authenticated_media_v1` (`PlaybackManager.cs:117`), so the new header-authenticated session recipe restoration is a server-side repair for an optional transport native does not negotiate. Desktop ticket requests already send bearer/profile/PIN/device proof (`SiloApiClient.cs:813`; `EventChannelClient.cs:673`, `PlaybackApi.V2.cs:166`, `PlaybackApi.WatchTogether.cs:112`), and the event client handles authority-change close 4001. Adding raw PIN/bearer headers to socket handshakes would be the wrong response; proof is delegated through the authenticated one-use ticket. Live restart/PIN/socket checks remain verification work, not a source-only compatibility certification. Sources: [restart design](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/restart-resilient-playback.md), [socket identity](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/internal/apiv2/socket_helpers.go), [realtime authority](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/realtime-api.md).

**Browser and server internals:** Safari/WebGPU/HDR renderer recovery and Chrome bandwidth-probe/auto-quality work target the browser engine, not embedded native libmpv. Redis/config validation, metadata matching, scans, rate limits, import memory bounds, profile-row cleanup and CI/lint updates are server-side. Do not copy browser code or add a desktop rewrite solely because these files changed. Sources: [Web decode architecture](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/web-decode-engine.md), [bounded history import](https://github.com/Silo-Server/silo-server/blob/9cc3091d6ec19996ee4f7149c7b72bfad3a0323f/docs/architecture/history-import-execution.md).
