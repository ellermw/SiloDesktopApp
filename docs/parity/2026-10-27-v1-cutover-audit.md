## Cutover contract and timing

The official contract requires removing legacy native aliases at 1.0: main API `/api/v1` roots/descendants get `410 Gone`, `client_upgrade_required`, `Cache-Control: no-store` and a migration link. It explicitly includes dynamic plugin URLs, media session URLs and download assets among surfaces needing restart/regeneration after cutover. Proxy/node routes have individual dispositions; their version-neutral spellings must not be blindly prefixed with `/api/v2`. Operational `/api/v1/health` and `/api/v1/ready` are retained probe exceptions. [Server contract, lines 1232–1289](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/docs/architecture/api-contract.md#L1232-L1289)

**The inspected main is still a bridge, not the actual tombstone implementation.** `internal/api/router.go:3162` mounts v2 and `:3164` still registers the v1 business surface. The official release sequence says merging v2 does not itself retire the bridge and retirement is a separate maintainer decision (#886). The user's next-Friday deadline is an operational requirement supplied by the user; this SHA does not establish a calendar cutoff date. A cutover verification must reject legacy routes itself or use the actual retirement candidate, because a successful smoke test against today's dual-stack server could hide legacy requests. [Lifecycle, lines 1761–1790](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/docs/architecture/api-contract.md#L1761-L1790), [current router](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/api/router.go#L3162-L3206)

## Required correction: embedded plugin pages still launch v1

**Confirmed runtime blocker:** `src/SiloPlayer/Views/PluginRoutePage.xaml.cs:55` builds `/api/v1/plugins/{installationId}{path}` and navigates WebView2 to it. Lines 53–54 incorrectly explain that dynamic-plugin exclusion means the versioned v1 prefix intentionally remains. At retirement, this page entry point hits the tombstone.

The replacement is **`/api/v2/plugin-content/plugins/{installationId}{path}`**, with static assets under **`/api/v2/plugin-content/plugin-assets/{installationId}/*`**. The proxy is excluded from *finite native operation schemas*, not excluded from migration. `internal/plugins/content.go:11` defines the common prefix; `internal/apiv2/plugin_content.go:41–55` documents its closed page/asset mounts and limitations; current WebUI's `web/src/lib/pluginRouteHref.ts:6` composes the replacement. [Plugin contract](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/docs/architecture/plugin-content.md), [content handler](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/plugins/content.go#L9-L91), [current href producer](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/web/src/lib/pluginRouteHref.ts#L1-L7)

Required implementation/verification details:

- Change the native launch producer and replace its misleading exclusion comment. Retain descriptor wildcard stripping/path escaping (`PluginRoutePage.xaml.cs:69`) and theme query behavior.
- Check `GET /api/v2/plugin-content/capabilities` for configured state or provide an actionable unavailable response. Capability availability does not prove an installation/route is enabled.
- Preserve canonical directory navigation: a page without its trailing slash receives same-origin 308 so relative SPA assets resolve under the installation. Current native root normalization yields `/`, which already provides that slash.
- Native WebView currently adds bearer and selected profile/PIN proof on same-server resource requests (`PluginRoutePage.xaml.cs:31–43`). The server's v2 page and asset adapters reuse session resolution (`internal/api/router.go:3145–3151`). WebUI instead calls `POST /api/v2/auth/plugin-launch` for its five-minute narrowly scoped cookie before full-page navigation. Native header injection may continue to be sufficient; verify both page and asset requests in the actual WebView rather than adding an unnecessary cookie flow or broadening cookie scope. [Web launch](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/web/src/lib/buildPluginHref.ts#L10-L45), [server wiring](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/api/router.go#L3145-L3151)
- Validate plugin public/authenticated/admin pages, protected-profile refusal, relative JS/CSS/images/fetches, static assets, forms and same-origin redirects. A changed account/profile while WebView is open must not silently use old page authority with new headers. This is an integration requirement, not proven by a URL-string test.
- **Changing the entry URL cannot fix arbitrary plugin-generated absolute v1 links, redirects or fetches.** Upstream deliberately does not rewrite them; each affected plugin needs compatible relative/versioned links and explicit evidence. V2 also refuses redirects to a different origin. Inspect deployed plugin content in the test fixture or representative local plugin; do not claim every third-party plugin is fixed by the desktop prefix change. [Proxy limitations](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/apiv2/plugin_content.go#L41-L55), [redirect handling](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/plugins/http_proxy.go#L204-L223)

## Dynamic URL paths: compatible projection, remaining guard gaps

`src/SiloPlayer.Core/Services/PlaybackDeliveryUrl.cs:5–18` is an intentional incoming-URL adapter. Relative `/api/v1/stream/*` and `/api/v1/playback/transcode/*` are projected to v2, retaining signed query bytes. Session-relative `/stream/{session}` sidecars constructed by `src/SiloPlayer/Services/PlayerService.cs:7246` pass through that resolver (`:3749`). These are not literal outgoing v1 calls. Upstream performs the same narrow local-delivery projection for stream, subtitle artifact/inventory and fonts in `internal/apiv2/playback.go:555–567`; its test verifies the original persisted plan is not mutated. [Projection](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/apiv2/playback.go#L555-L567), [sidecar projection test](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/apiv2/playback_delivery_test.go#L290-L307)

## Saved URLs and stale references

- `ServerWebUiUri.cs:12–14` strips a trailing `/api/v1` or `/api/v2` when opening the server WebUI. This is incoming saved-URL compatibility and emits a WebUI root, not v1 traffic.
- This does **not** normalize the actual API base or saved credentials: `ServerUrlIdentity.cs:26–50` retains the path; `AuthService.cs:64–75` configures it; `SiloApiClient.cs:293–310` only trims trailing slashes; `:410–413` concatenates base and route. A hypothetical old saved base `https://host/api/v1` therefore becomes `/api/v1/api/v2/...`, whereas normal saved origin URLs work. No user settings/credentials were inspected. ## Implementation follow-up — Task 1, same day

The preceding sections preserve the audited 312 baseline. Task 1 now changes the source as follows; final packaged verification is recorded separately by the integrating task.

- Plugin entry navigation uses `/api/v2/plugin-content/plugins`, including canonical root-directory normalization. Same-server requests use a captured owner and an atomic header snapshot; a later profile/account cannot lend credentials to the earlier document. Stale ownership gets a local403/reopen message; same-server retiring plugin resources get a local410/plugin-update message. External document navigation is cancelled and external resources receive no injected credentials.
- `NativeApiRetirement` detects path segments belonging to retiring HTTP API v1 resources, including deployment prefixes, casing and escaped separators. Playback keeps only the documented relative local-delivery projection; stale absolute or unsupported v1 resources require refresh/restart rather than signed-URL rewriting.
