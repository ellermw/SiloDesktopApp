### F01 — P1 — Settings detail shell has different geometry and responsive chrome (SC)

WebUI `SettingsLayout.tsx:588-619` encloses rail and content in one `surface-panel-lg`, with **240px rail** (`w-60`), right border, sticky rail, minimum 500px height, content padding 16/24px and **768px cap** (`max-w-3xl`) except Devices. Native `SettingsPage.xaml:132` creates a plain two-column Grid; `.xaml.cs:167-205` uses **220px**, adds **40px left content padding**, and sets `MaxWidth` to infinity. WebUI CSS shell is max **1520px**, desktop horizontal padding **40px** before 1280 then **48px**; native shell max **1424px** with fixed 48px margin at all widths >=1024. Below 1024 WebUI hides the big Settings header/search on detail pages, leaving All settings; native keeps the 48px Settings header and search visible. The resulting spacing/layout is a source-confirmed mismatch across all tabs.

Evidence: [WebUI shell](https://github.com/Silo-Server/silo-server/blob/8e2e840474a085c6df6571a5a2850f7eb996810c/web/src/pages/SettingsLayout.tsx#L588), [CSS widths](https://github.com/Silo-Server/silo-server/blob/8e2e840474a085c6df6571a5a2850f7eb996810c/web/src/app.css#L1910); [native shell](C:/Users/Michael/.codex/worktrees/parity-top-three/SiloPlayer/src/SiloPlayer/Views/SettingsPage.xaml:64), [native resize](C:/Users/Michael/.codex/worktrees/parity-top-three/SiloPlayer/src/SiloPlayer/Views/SettingsPage.xaml.cs:134).

## API and interaction acceptance boundaries

Source inspection establishes native API calls for credential providers/device login/OAuth, profiles/avatar/PIN, settings contract values/effective/capabilities, home sections and layout transfer, history import/auth/source/run events, notifications destinations, providers authentication/sync and webhook connections/mappings/deliveries. Those wrappers are not runtime proof of current response shapes, action eligibility or save semantics.

For every mapped surface, verify the following without using feature existence as a completion criterion:

1. Route/deep-link/back history and required-auth/profile/primary/admin/view-as guards; no stale account/profile values after switching. Distinguish source presence from dispatch reachability.
2. Loading skeleton geometry, empty state, unsupported capability, permission-disabled state, failed fetch/retry, server validation, write pending, uncertain completion, cancel and successful refresh.
3. Effective scope: server/default, profile, client family, profile-device, library/item; reset deletes override where required; locked values stay read-only; unsupported key revisions do not produce controls or requests.
4. Icons and labels: WebUI lucide symbols versus native Segoe Fluent glyphs must match meaning, size, alignment, stroke impression and accessible name. Button existence is not icon parity.
5. Typography/colors/radius/spacing/borders/scrims/shadows: compare actual light/dark/high-contrast branding tokens, 100/125/150/200% DPI and extra-large text. Fixed XAML pixel settings do not prove CSS-like relative sizing.
6. Keyboard Enter/Escape/Tab/Shift-Tab/arrows/Ctrl-K; UIA names/selected/pressed/disabled/live status; focus placement and retention after async errors; popup traps and drag keyboard alternatives.
7. Realtime/cache changes and revisit behavior. Native Settings uses cached page and a two-minute stale threshold; validate each lazily constructed tab/control re-fetches appropriately after profile/capability changes. Source review has not proven all tabs refresh correctly.
8. Native additions (server selection, local bitstream/upscaling, browser subscription handoff, Sessions) need explicit product acceptance. WebUI route absence should not be described as a missing desktop feature.

No routes or controls in this report are marked parity-complete. The highest-priority concrete changes for a future implementation pass are F17 (overlay masters/inheritance reset), F03 (device current contract/lock/platform controls), F01/F02 (shared settings shell/group geometry), then F13/F14 (branded and navigable recovery/required-password views). This audit itself makes no implementation changes.
