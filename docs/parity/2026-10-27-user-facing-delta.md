## Concrete update groups, in suggested order

### 1. Correct metadata lock mapping and Reset to Provider

The tagline belongs to the overview lock (1), while native `src/SiloPlayer.Core/Services/MetadataEditState.cs:14` puts it under the name lock (0). Native `Set` automatically applies that mapping (`:35-38`), so a tagline edit writes the wrong protection. The current WebUI corrects this mapping in `web/src/components/EditMetadataDialog.tsx:63`.

Native Reset (`src/SiloPlayer/Views/Dialogs/EditMetadataDialog.cs:121-133`) only requests refresh. Current WebUI first saves `locked_fields: []`, closes only after that succeeds, then requests refresh (`EditMetadataDialog.tsx:244-258`). This matters because refresh honors locks: native's existing promise that provider metadata will replace edits is ineffective for locked fields. The reset also needs to be held during image apply as well as metadata save: native's reset handler checks `_pending` but image apply tracks separate `_imagePending` (`:465`). Preserve unsaved edits when unlocking fails and prevent a finishing write from re-locking after reset.

Source: [manual-edit and cache repair cc1a496](https://github.com/Silo-Server/silo-server/commit/cc1a496a3d1ed0e051cba4dd4ae4165e5f2967e1), [current WebUI reset and mapping](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/web/src/components/EditMetadataDialog.tsx#L60).

Verify: tagline-only edit survives refresh without locking the title, explicit lock changes, reset of locked metadata/artwork, failed unlock, save/apply/reset overlap and refreshed Home/detail identity/artwork. The lifecycle Status selector mentioned again in this upstream commit was already removed locally in the October 24 work; `MetadataEditState.cs:22` has no status field, so it is not another new update group.

### 2. Consume the configured Requests Discover layout and current pagination

The viewer endpoint now returns `row_order` alongside `items`: title and brand rows can be interleaved, renamed, hidden or removed. New custom title rows have opaque IDs and must page through `/api/v2/requests/discover/rows/{row_id}`; the old `/{section}` operation only serves built-ins. The status resource advertises `discover_rows_supported`. These are viewer concerns even though the editor itself is server administration.

Native `src/SiloPlayer.Core/Api/RequestsApi.cs:28-32` deserializes only a generic collection's `Items` and retains the old pagination route; `Models/Requests/MediaRequests.cs:95-98` has no row order. `src/SiloPlayer/Views/RequestsPage.xaml.cs:405-435` renders title rows first, then `:514-521` unconditionally renders all three brand groups. `RequestsViewModel.cs:81-85,161-181` loads every brand regardless of layout. Consequently custom title rows can appear in the initial response but their Explore All uses an incompatible route, while removed/hidden brand rows still appear and interleaving is lost. Unknown row types must be skipped. Preserve old-server fallback using the capability/response shape; do not hard-code only the new server default.

Two related continuation problems are concrete: `src/SiloPlayer.Core/Services/RequestDiscoveryPaging.cs:8-10` stops whenever `next_page` is absent, but the current contract explicitly says absence means ordinary page+1 where pages remain. A cursor beyond `total_pages` or one that fails to advance terminates traversal. `RequestsPage.xaml.cs:420` only exposes Explore All when `TotalPages > 1`; rows trimmed to an admin limit can have more titles even when the source has one page, so the additional `TotalResults > Results.Count` condition is needed. These are one integration group with layout/row paging, not a request to add an admin layout editor.

Source: [Discover layout 9b84f13](https://github.com/Silo-Server/silo-server/commit/9b84f13a8aa611aa73e2d1fd354c72c0ea5f6d82), [viewer shape and routes](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/apiv2/requests.go#L143), [WebUI layout rendering](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/web/src/pages/Requests.tsx#L181), [cursor behavior](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/web/src/hooks/queries/useRequests.ts#L121), [layout architecture](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/docs/architecture/request-discover-rows.md).

Verify: title/brand interleaving and custom labels, hidden/all-disabled/empty/unknown rows, old server, failed row/brand loads, opaque IDs, changed/deleted row while browsing, source page without cursor, multi-page filtering cursor, cursor past end/nonadvancing, one-page source trimmed to a smaller rail limit and duplicate suppression.

### 5. Correct uploaded-current display in the existing image editor

Upstream adds an acting-admin, nonretryable multipart `POST /api/v2/admin/items/{id}/images/upload` (`type`, `image`), accepting JPEG/PNG/WebP up to 10 MiB. Movies/series accept poster/backdrop/logo; seasons accept poster only. Applying is immediate and locks images. The uploaded image is listed as a local choice only while current; `original_url` is `upload://sha256:...`, while `current.poster_url` etc. remain stored paths. There is no permanent upload gallery to recreate.

Native already has an exposed maintenance UI: `src/SiloPlayer/Views/Dialogs/EditMetadataDialog.cs:366-479`. Its current-image detection compares original_url with current stored path (`:417,436`), so it fails to mark an image uploaded in WebUI as Current. The WebUI explicitly recognizes an `upload://` choice as current because the server lists it only while current. Correct this display and treat `upload://` as the opaque returned identity rather than a URL to fetch. Existing apply already sends original_url unchanged (`:466`), so do not create a new image-download path.

**Optional new privileged feature, outside required non-admin parity:** native `src/SiloPlayer.Core/Api/MediaMaintenanceApi.cs:27-48` has list/apply only and the editor has no upload button. Adding a file picker and multipart upload would extend the native administrative feature set; it is not required merely to preserve the existing image picker. If separately chosen, enforce the same type/size constraints with server byte validation authoritative, share pending gating with apply/save/reset, reload image choices/detail, refresh lock state and emit the existing surface-change signal.

Source: [upload e6df1d8](https://github.com/Silo-Server/silo-server/commit/e6df1d8eddce823a7bfd4ac2c513e9e83d835277), [multipart contract](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/internal/apiv2/admin_catalog_images.go#L45), [WebUI validation/pending/current display](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/web/src/components/ImageSelectorTab.tsx#L25), [storage/lifetime](https://github.com/Silo-Server/silo-server/blob/564b906b8eb529c77c5e0b5c640aa13c1133c7f1/docs/architecture/local-nfo-metadata.md#L625).

Verify the existing editor: current uploads originating in WebUI, provider replacement, textless filter, context change and image lock/reset behavior. If optional native upload is added, also verify each allowed content/type combination, type/byte mismatch, oversized/invalid/canceled file, unavailable storage, failure/retry without duplicate mutation replay and same bytes twice.
