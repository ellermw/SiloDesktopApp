# 1.2.378 — installer and build-output safety

Fourteen independently meaningful behavior changes over364 give378. Tests support these behaviors; builds and assertions are not separate increments.

1. Refuse populated foreign installation folders before clean-payload deletion.
2. Recognize upgrades using Silo's registered AppId/install location and executable, rather than generic filenames.
3. Refuse system, account/data and source/evidence roots as install destinations.
4. Refuse linked or inaccessible installation-path components.
5. Refuse linked contents or uninspectable/deep trees in an existing registered installation.
6. Remove recursive uninstall deletion; uninstall removes logged files and preserves unrelated additions.
7. Refuse filesystem roots and repository ancestors as publish targets.
8. Preserve every existing populated publish target, including frozen payloads, installed apps and fake executable markers.
9. Give each default build a fresh publish-GUID directory; explicit custom targets must be new/empty.
10. Refuse linked publish-path components.
11. Refuse system/application/account-data locations as build outputs.
12. Constrain build configurations to Debug/Release before path construction.
13. Preflight generated bin/obj cleanup containment and linked entries before literal-path deletion.
14. Read only two bytes for the libmpv PE signature instead of loading the whole library.

A registered Silo install directory remains the dedicated disposable application payload for a clean upgrade; arbitrary additions inside that directory are not promised to survive an upgrade. Keep personal files outside it. The new uninstaller preserves unrelated additions; older uninstallers retain their previous behavior until replaced. Portable/unregistered populated folders must use a new/empty install destination. Custom build targets are no longer overwritten or recursively cleared.

Actual Pascal runtime verification uses unrelated fixture identities, lowest privileges and dummy files, with no production SDK/firewall/protocol/shortcut/app-launch actions. It covers refusal cases, fresh install, registered clean upgrade removing obsolete runtime files, and uninstall preserving an unrelated file. Default and explicit custom supported builds are verified separately. Full/current source, installer hashes and publication receipts are in `docs/current-development.md`. The installed player is not replaced or restarted by publication; actual elevated updating and previous hardware/phone/full-parity limits retain their separate verification requirements.
