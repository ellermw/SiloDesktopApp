# Core architecture audit — installed .101 preview and matching working source

Read-only review of every non-generated file under `src/SiloPlayer.Core`, plus the explicitly listed tests in `backend-coverage.json`. The installed .101 preview PDB source hashes were matched to this source by the parent audit; the project version label is .100. No source or app state was changed. Findings below are source-established, with runtime reproduction and fresh server-contract verification distinguished explicitly. This is an architecture audit, not a claim of full visual parity or a diff review. The current README makes this a user-only desktop client; retained item match/refresh permissions do not imply an admin console.

## Rebuild decision

Keep .NET, native libmpv, long-lived HttpClient transports, Windows Credential Manager, explicit direct/HLS transport and timeline models, bounded retry history, and the small pure policy classes. The recent recovery relay is substantive engineering: it validates byte ranges, tracks entity identity, resumes interrupted reads without concatenating a changed entity, and has meaningful fault-injection tests. Presigned artwork is cached as bytes, with signature normalization and bounded memory/disk targets. These are useful foundations worth retaining.

Change the ownership model around that foundation. A new implementation should have one immutable authenticated context (server, account, profile, credentials, generation), one playback-session owner that serializes every mutation, one cancellable realtime owner per context, and a bounded artwork service with its own lifetime. Cache keys, request headers, response application, event delivery, and disposal should derive from those owners. Today each service partially implements its own generation, lock, CTS, and cache invalidation convention; the seams between them are the weakest part of the system.

Replace the reflection-based request serializer, mutable settings persistence, and callback/task-based realtime lifetime management. Split transport DTOs from mutable UI presentation objects, and split the broad SettingsApi/model file into user-settings features. Prefer a generated System.Text.Json context with explicit request DTOs and contract fixtures over dictionaries and handwritten top-level property reflection. A whole-application rewrite is not justified by the Core review; targeted replacement of state ownership provides a better migration path.

## Findings

### B01 — Playback replans can publish after session replacement (high confidence, high impact)

`D:/SiloPlayer/src/SiloPlayer.Core/Services/PlaybackManager.cs:458` captures the current session/plan, awaits the replan at line 514, and applies it at 515–526. Its replan semaphore serializes replans only. `StartSessionAsync` at 99 and `StopSessionAsync` at 671 do not participate in that ownership protocol. A delayed quality/audio/subtitle replan completing after stop or new-content start can restore old session fields and stream state. Audio/subtitle entry points also evaluate retained quality before they acquire the replan gate, so concurrent quality and track changes can overwrite a newer quality choice. The parent review independently found that PlayerService uses different play, seek and stream-mutation gates, and audio transport preparation occurs before its final session guard, so Core cannot rely on a single external serializer.

Replace with a session-scoped command loop or common mutation gate plus generation checks after every await. Prepare transports as owned candidates; only the current generation may atomically publish one. Dispose rejected candidates without touching the active transport. Add deterministic delayed-replan versus stop/start/quality tests. Existing manager tests cover progress cancellation, cleanup deadlines and session replacement, but not these crossed operations.

### B02 — Proactive refresh cancels its own authoritative account refresh (high confidence, medium impact)

`AuthService.cs:341` calls `ScheduleRefreshUnsafe` while the scheduled `TryRefreshAsync` is still active. Scheduling calls `CancelRefreshScheduleUnsafe` at 571, which cancels the old schedule CTS at 600. That is the token then passed to `/auth/me` at 362–365. Therefore the normal proactive success path saves rotated tokens, schedules another refresh, then aborts its authoritative user lookup. Authentication survives, but permission/role changes may remain stale. Token expiry policy, terminal/transient classification, refresh serialization, server snapshots, generation validation and durable rotation are otherwise good work to keep.

Separate the cancellable delay from the active refresh operation, and test scheduled renewal all the way through an updated `/auth/me` response. Current scheduled-refresh tests establish that refresh occurs, not that account reconciliation succeeds afterward.

### B03 — API requests can mix endpoint and credential contexts (high confidence in interleaving, runtime not reproduced)

`SiloApiClient.cs:202` builds a URL under one state read; `AddHeaders` at 527–537 takes a later state read. A server/account switch between those operations can attach the replacement session's credentials to a URL built for the previous server. Authentication generations prevent a stale 401 from clearing a new session, but do not make initial URL/header construction atomic. Build each request from one immutable context snapshot and reject stale responses before applying them. Capture websocket URL and ticket/auth inputs from the same context too.

### B04 — Realtime run-loop lifetime is race-prone and retains stale snapshots (high confidence)

`EventChannelClient.cs:145`, 162 and 194 use `Task.Run(() => RunLoop(_cts.Token))`, closing over a mutable field. A reconnect before the delegate starts can make an older task use the replacement token; both loops may then remain live and overwrite the shared socket. Cancellation at 179–183 does not dispose old CTS instances. `_latestSnapshots` at 35 is keyed only by channel and survives stop/logout/reconnect; `TryGetLatestSnapshot` at 63 exposes that retained state. Whether users see stale data depends on each subscriber, but the cache itself is not account/profile isolated.

Receive processing at 436 decodes each websocket fragment separately with UTF-8, which can corrupt a multibyte character split between receives. The message StringBuilder has no size bound. Graceful close at 395 uses CancellationToken.None. Replace with a connection object containing immutable token, socket, bounded byte buffer and task; cancel, await and dispose that object. Scope snapshots and subscriptions to the authenticated context, reconnect on profile changes, and decode after message assembly or use a Decoder. Add a fake websocket seam for reconnect, fragmented Unicode, large-message and profile-transition tests. There are no direct runtime EventChannelClient tests in this review.

### B05 — Sixteen stalled image bodies can exhaust artwork delivery (high confidence)

`ImageService.cs:135` starts shared downloads with CancellationToken.None. Consumer `WaitAsync(ct)` cancels only the wait. The response is streamed after headers and `CopyToAsync` at 199 has no image-body size cap or service-owned deadline. Sixteen bodies that stop sending can retain all semaphore slots. Navigation cancellation cannot release them; speculative requests also have no bounded backlog. `Dispose` at 460 disposes the semaphore while retained jobs may later release it at 219. The cache size target limits completed cached bytes, not the size of an active response or outstanding work.

Keep content-aware signature normalization, disk-byte caching, atomic file move, expired-URL refresh and coalescing intent. Add service lifetime, per-download total/idle deadlines, maximum encoded bytes and decoded pixels, bounded priority queue, cancellation/refcounts for unneeded work, and async disposal. Distinct signed URLs currently create separate in-flight entries even for one disk key. Memory-byte accounting also races ClearMemoryCache at 225–227 against writers. Existing image tests cover signature handling, fallback and successful caching; add hung-body, large-body, disposal and concurrent eviction tests.

### B06 — Settings persistence is non-atomic and exposes mutable shared state (high confidence)

`SettingsService.cs:30` performs synchronous load and deserialization with no malformed-file recovery; Save at 48–55 updates the cached object and directly overwrites settings.json. An interrupted or failed write can leave a truncated file that prevents the next load, while memory already reports the new settings. Load returns the live mutable object, so callers mutate it outside the lock; Load-modify-Save operations are not atomic transactions. The per-book speed dictionary uses content ID without server/account/profile identity. Other global IDs deserve the same scope audit.

Replace with immutable snapshots, serialized update transactions, versioned schema, asynchronous/debounced atomic temp-file replacement, and last-good recovery. Keep secrets exclusively in the existing credential store. Current persistence tests cover a successful round trip and the 50-book cap, not corrupt JSON, failures, concurrent updates or multiple servers.

### B07 — Request serialization has two conflicting contracts (high confidence)

`SiloApiClient.cs:461` uses handwritten top-level reflection: it drops null values, ignores JSON attributes, and inserts an underscore before each uppercase letter. Nested values use System.Text.Json's separate naming/attribute policy. A request with acronym names, JsonPropertyName/JsonIgnore or explicit-null reset semantics can have different top-level versus nested behavior. The Core project is explicitly not trimmable, while source tests enforce dictionaries as “trim safe.” This historical workaround should not define the new transport architecture.

Use generated/typed serialization and assert emitted JSON against captured authoritative fixtures. Also validate required response fields: the null-forgiving deserialization return at 692 does not prevent a JSON null result or missing required playback IDs. Broad `object` payloads and mutable DTO defaults move schema errors into distant playback/UI code. Many model classes are straightforward and can stay as wire DTOs, but separate their computed presentation fields and collections from request payloads.

### B08 — Cancelled 401 waiters can leave HTTP responses undisposed (high confidence)

`SiloApiClient.cs:593` receives the first response, then awaits `_refreshLock` at 604. Cancellation there, or a throwing refresher at 617, can exit before the response is returned to the outer `using`. There is no surrounding ownership/finally for that response. Repeated cancelled unauthorized requests can hold response resources/connections. Ensure the retry helper owns and disposes every rejected response on all exits; add cancellation-at-refresh-gate and throwing-refresher tests. The existing safe-method/replay, generation, redirect and auth-retry tests are worth keeping.

### B09 — Default version ranking can escape the quality preference (high confidence)

Verification update: the parent executed the compiled current Core helper against the three-file case below. It selected file 3 at 2160p despite the 1080p preference. See helper-behavior-probes.json. This reproduces helper behavior, not the full application selection flow.

`VersionRanking.cs:71` filters for preferred resolution only inside PickBestAttributes, then independently aggregates best resolution, any HDR, and best audio across files. SelectDefaultVersion at 143 requires that composite to exist in one file (and checks top-level audio rather than its full audio-track inventory). If it does not, line 152 chooses highest resolution from the original edition candidates. For example 1080p HDR/AAC, 1080p SDR/TrueHD and 2160p HDR/TrueHD with preference 1080p produce a nonexistent 1080p HDR/TrueHD tuple and fall back to 2160p. Rank actual files lexicographically within the filtered set. Keep explicit edition/last-file semantics and test contradictory attributes plus audio-track versus primary-codec cases.

### B10 — Stall detector loses small cumulative advances (high confidence in helper behavior)

`PlaybackStallDetector.cs:62` resets the advance timer only if a single sample changes by more than the significance threshold, while line 71 replaces the comparison position on every smaller observation. Repeated sub-threshold progress can eventually be declared stalled although total progress is healthy. The parent executed the compiled current Core helper with 0.5-second advances, moving from position 100 to 115 over 30 seconds: ShouldRecover became true with position-stalled. See helper-behavior-probes.json. PlayerService.cs:1926 samples every second and :2240 does not exclude audiobooks, so this matches supported 0.5x audiobook playback under regular sampling; real timing jitter can change when it triggers. This is reproduced helper behavior and source-established application reachability, not an observed full-app incident. Compare against the position at last significant advance or detect monotonic accumulation. Current tests use large discrete steps or exactly stationary playback and miss frequent small steps.

### B11 — Direct relay header acquisition lacks its own deadline (high confidence, mitigated impact)

`DirectStreamProxy.cs:399` creates an infinite-timeout HttpClient. `DirectStreamRelay.cs:132` sends upstream headers with only the proxy lifetime token; the idle deadline at 364 applies to subsequent body reads. An upstream that never returns headers cannot activate the relay's idle recovery. Parent found a 15-second initial player-load watchdog and later stall recovery, so this is a transport robustness gap rather than proof of an indefinitely frozen player. Keep the relay's strict range/entity validation and bounded recovery; add explicit connect/header budgets and a headers-never-arrive test.

### B12 — Credential attachment to subtitle URLs needs one origin policy (high confidence in API behavior, external URL reachability unverified)

`PlaybackManager.cs:781` resolves subtitle URLs then appends the account access token at 794 through `Helpers/UrlHelper.cs`. That helper does not check whether an absolute URL is same-origin, already signed or a third-party artwork/subtitle host. If the server returns such a URL, the account bearer token is disclosed in its query. Current routing may return only server-relative subtitles; verify before calling this an observed leak. The newer direct proxy explicitly separates signed URLs from account authorization, which is the correct pattern to generalize.

## Efficiency and maintainability observations

* Catalog library caching (`CatalogApi.cs:25`) is global, mutable and five-minute TTL based; invalidation does not prevent a late pre-transition fetch from repopulating it. Item-detail prefetch is better: context-keyed, coalesced and bounded, but evicted requests continue with CancellationToken.None. Watch-detail prefetch accepts profile identity only. Centralize cache context and response-generation rules instead of relying on every caller to invalidate.
* Ebook file APIs return complete byte arrays (`EbooksApi.cs:10`; SiloApiClient byte buffering), which puts large comic/PDF payloads on the managed large object heap before the reader writes or decodes them. A streamed file/cache handle is the more efficient boundary. The API retry path also prebuffers request bodies for replay, so uploads incur extra copies.
* `MediaItemCollectionReconciler` keeps mounted object identity, a useful UI strategy, but scans/moves linearly per item and serializes nested audiobook/ebook objects for equality. That is quadratic for long lists and allocates on likely UI paths. Keep incremental updates; use keyed immutable render snapshots and measured diff budgets. Separate wire models from ObservableCollection and display calculations.
* `LocalLog` serializes synchronous file IO under a global lock. Redaction and bounded rotation are useful, but adopt structured events and a bounded writer queue; consolidate the separate URL redactor so signed path tokens are not missed.
* Small policy classes (timeline, recovery history, next-episode ownership, card geometry, virtual slots, browser/ebook URL restrictions, authorization, capability declaration) have concise interfaces and focused tests. Keep them, move presentation geometry out of a nominal domain Core if splitting projects, and avoid introducing interfaces for every pure helper.
* Defensive parsing has small holes: ThumbhashDecoder permits a five-byte alpha hash then reads byte 5; FlexibleNullableDateTimeOffsetConverter can overflow Math.Abs(long.MinValue); SubtitleAppearance's TryGetInt32 can throw on a string value despite its forgiving-parser contract. SubtitleAutoSelect has its own older language alias normalization separate from MediaLanguageCatalog. Consolidate normalization and fuzz untrusted parsers.
* The remaining broad settings/model namespaces and protocol-v2-shaped playback response adapter obscure the user-only/v3 contract. Keep compatibility behind an explicit adapter while migrating; remove unused legacy members after call-site inventory, not just because their names look administrative.

## Test assessment and rebuild sequence

The suite has real value in fake HTTP handler tests, asynchronous completion controls, entity/range relay recovery and cache behavior. Source-text assertions are also numerous: ServerContractSourceTests, ApiPayloadSourceTests and parts of playback/auth parity tests can pass with the right words present while behavior is broken. They are architecture guards, not evidence of server interoperability, visual parity, thread safety or actual native rendering. Tests that merely mirror constants should not dominate confidence.

First add deterministic lifetime interleaving tests for the confirmed issues. Then migrate session ownership and immutable authenticated context, preserving the existing transport policies. Replace artwork lifetime and settings persistence independently. Introduce typed wire contracts with fixtures from a recorded official GitHub commit, then prune dead v2/admin-shaped surface behind proven call-site analysis. Finally measure high-bitrate playback, frequent seeks/track changes, long profile-switch sessions, large-library artwork load, and managed/native memory under repeated navigation. This reviewer did not run tests or operate the installed app; execution evidence belongs to the parent audit.

Exact per-file coverage and physical line counts are in `backend-coverage.json`. “Full read” means the complete source/test file was reviewed, not that every feature was executed. Generated bin/obj artifacts are excluded; no in-scope Core source file was unreadable.
