These findings describe current source, not necessarily the installed Apple build.

## Findings

1. **Apple has a substantial local media transport layer.** The app passes the resolved source URL and headers into Aether. For original media, Aether's documented pipeline is HTTP → FFmpeg demux → local HLS/fMP4 mux → loopback HTTP → AVPlayer. This local remux must not be confused with a Silo server remux plan. Server HLS plans explicitly select `nativeRemoteHLS`, so the original-file pipeline should not be generalized to all routes. The macOS view and iOS/tvOS view use the shared `PlayerViewModel`; this is not evidence of distinct platform retry implementations. [Pinned dependency](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/project.yml#L56-L61), [source load](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/AetherPlaybackController.swift#L188-L198), [engine pipeline](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/AetherEngine.swift#L17-L37), [server HLS selection](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/AetherLoadSpec.swift#L442-L466), [macOS view](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/macOS/PlayerView.swift#L22), [shared mobile/TV view](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerView.swift#L17-L45).

2. **Network recovery first stays on the source.** Aether's persistent playback reader uses Range requests and reconnects at the delivered-byte frontier after stalls or premature connection end. Current constants include a 20-second no-data threshold, 32 MiB bounded ranges, a 16 MiB default forward window, and a 512 KiB progress threshold that resets the unproductive retry streak. The established-source give-up check is `unproductiveReconnects > 12`; never-productive sources have a lower cap of 4, while hard HTTP errors before any bytes get one retry. Normal range completion and backpressure refill do not spend this retry budget. After reader exhaustion, the VOD engine also has a bounded fresh-demuxer recovery path anchored to the current playback/pending-seek position. These are engine recovery mechanisms before the application receives a terminal `vodSourceFailed`. Unknown-size streaming is a separate reader mode documented without reconnect; these guarantees are not universal. [Reader modes](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/Demuxer/AVIOReader.swift#L6-L14), [buffer and retry constants](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/Demuxer/AVIOReader.swift#L543-L583), [reconnect decisions](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/Demuxer/AVIOReader.swift#L1937-L2018), [give-up criteria](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/Demuxer/AVIOReader.swift#L2051-L2078), [VOD producer revival](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/Video/HLSVideoEngine+LiveReopen.swift#L373-L445).

3. **A stall is not itself a server fallback signal, but terminal network errors can be.** The app maps `.loading`, `.rebuffering`, and `.stalled` to its loading UI. A committed V3 load can request a replan for typed errors including `sourceRefused`, `vodSourceFailed`, `nativeItemFailed`, and decoder/format failures. Therefore the claim that Apple never changes routes for network problems is unsupported. Its important distinction is the preceding engine recovery and typed error classification. `sourceRateLimited` is explicitly separate: HTTP 429/503/509 causes paced retries, and once exhausted the app displays a delay notice rather than immediately entering the server-adaptation branch. The generic classifier also distinguishes `network_degraded`, `decoder_error`, and `unsupported_stream`. [Stall UI handling](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerViewModel.swift#L1137-L1144), [typed fallback policy](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerViewModel.swift#L1320-L1356), [generic classification](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerViewModel.swift#L2168-L2182), [typed HTTP/read failures](https://github.com/Silo-Server/AetherEngine/blob/f8239c206097c88b53492b281af15cf906c8295b/Sources/AetherEngine/PlaybackErrorInfo.swift#L20-L59).

4. **Current V3 transport supports header authentication, with same-plan credential recovery.** `StreamRequest` adds the current Bearer header. Header-authenticated media normally requires validated API-relative routes; negotiated authorized media origins permit a restricted absolute proxy URL pinned to the session. This is not evidence that current Apple playback depends on signed media query URLs. A typed 401 or AVFoundation authentication-required failure first gets a chance to refresh authentication. Reload happens only if the Authorization value changed; it preserves the plan, source-time resume point, and intended play/pause state. A successful periodic progress call can also trigger this reload after token rotation. [URL/header policy](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/StreamRequest.swift#L9-L117), [typed auth policy](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/AetherLoadSpec.swift#L46-L88), [refresh/reload entry](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerViewModel.swift#L1479-L1508), [resume preservation](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerViewModel.swift#L1684-L1706).

5. **Heartbeat failures do not immediately downgrade media.** Progress runs every 10 seconds with position and pause state. A missing session requests renewal; other failures remain transient, with a warning after three consecutive failures. Buffer-ahead choices pass 10 segments (~40 seconds), 75 (~5 minutes), or an engine-clamped maximum; automatic delegates to other settings. These local buffering preferences are distinct from server transcoding and from the reader's byte window. [Heartbeat loop](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerViewModel.swift#L7383-L7406), [progress failure handling](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlaybackSessionBridge.swift#L1854-L1897), [buffer preference mapping](https://github.com/Silo-Server/silo-apple/blob/71299aa302f5ce60d0d9e4b36c530a70aea8b236/iosApp/iosApp/Screens/Player/PlayerSettings.swift#L40-L70).

## Implication for the Windows investigation

The useful comparison is layered recovery and preservation of failure meaning: reconnect/reopen a previously productive source before declaring the route unusable, keep rate limiting and authentication separate from codec incompatibility, and preserve position and play intent. This source review alone does not establish the cause of the reported Windows stall or prove any particular timeout/cache setting will fix it.
